MotionServe: Efficient Multi-Robot Serving by Exploiting Robot Execution Slack

02论文概述

  • 论文提出 MotionServe，一个面向多机器人 VLA（视觉-语言-动作）模型的高效共享 GPU 推理服务系统
  • 解决的核心问题：在多机器人场景下，如何平衡机器人观测时机与服务器端批量调度，以充分利用机器人执行缓存中的“执行冗余”（execution slack），避免机器人因等待推理结果而停滞
  • 通过结合 LoRA 低秩适配 实现多策略共享主干网络，同时利用动作块（action chunking）中的剩余执行时间协调请求生成与批量推理

03核心贡献

  • 提出 MotionServe 框架，将多 LoRA 服务引入多机器人 VLA 部署，利用执行冗余协调观测时机与批量形成
  • 开发 MotionExec，一种运动引导的流水线动作执行机制，根据预测动作块的运动结构选择观测触发点，使推理与剩余缓冲执行重叠
  • 开发 SlackBatch，一种冗余驱动的异步批量调度器，结合每个机器人的执行冗余与 GPU 未完成工作估计，决定何时等待、哪些请求组成批量以及何时派发
  • 在 X-VLA 与 OpenVLA-OFT 模型上验证，证明共享主干可将 96 个策略的权重内存降低 97.6%（X-VLA）和 91.1%（OpenVLA-OFT）

04方法描述

  • MotionExec（运动引导流水线执行）：对预测动作块做两段线性拟合，寻找运动过渡的“最佳观测点”（sweet spot），使机器人在执行该动作后触发新观测请求，同时继续执行剩余缓冲动作，从而创造执行冗余
  • SlackBatch（冗余驱动异步批量）：根据每个机器人请求的缓冲区耗尽截止时间计算 GPU 完成预算，按预算排序并分组；当整批请求的调度余量（dispatch margin）为正时等待，余量耗尽时提交可行的最大请求组，避免机器人停滞
  • 共享 LoRA 骨干：所有机器人策略作为同一冻结 VLA 骨干上的轻量适配器进行混合批量推理，减少权重内存并支持跨策略批量
  • 观测触发与批量调度闭环：机器人端返回新的最佳观测点，服务器端调度器依据剩余冗余决策派发，形成端到端协调

05数据集与资源

  • 模型：X-VLA（动作块长度 30）和 OpenVLA-OFT（动作块长度 8），每个任务为一个独立 LoRA 适配器（X-VLA rank=8，OpenVLA-OFT rank=64）
  • 数据集/环境：LIBERO 四个任务套件（Spatial、Object、Goal、Long）与 SimplerEnv 的 WidowX-250 仿真任务（Stack Cube、Carrot、Eggplant、Spoon）
  • 机器人仿真：LIBERO 使用 Franka Panda 臂，SimplerEnv 使用 WidowX-250 臂；每个机器人每 episode 采样动作周期 0.1–2.0 秒
  • 硬件资源：4 块 NVIDIA H200 SXM GPU（每块 141 GB），其中 1 块用于共享推理，3 块用于机器人仿真；机器人规模最多 96 个
  • 软件栈：PyTorch 2.11，BF16 精度，使用 fused SGMV LoRA 内核

06评估与结果

  • 评估指标：内存占用、可驻留策略数、机器人平均停滞时间、任务成功率、任务吞吐量
  • 内存与容量：在 96 个策略下，共享部署将权重内存从独立部署的 7.52 GiB（X-VLA）和 123.35 GiB（OpenVLA-OFT）进一步降低 97.6% 和 91.1%；单块 H200 可驻留策略数从 43（X-VLA）/9（OpenVLA-OFT）提升至 3,114 和 111
  • 机器人停滞时间：在 96 机器人规模下，MotionServe 将 X-VLA 的平均停滞从 4.87 s/episode 降至 2.76 s（降低 43.4%），将 OpenVLA-OFT 从 20.04 s 降至 13.50 s（降低 32.6%），均优于所有基线
  • 任务成功率：在 96 机器人规模下，X-VLA 平均成功率提升 8.98 个百分点（至 62.35%），OpenVLA-OFT 提升 2.30 个百分点（至 95.68%）；MotionServe 在成功率-停滞权衡图中始终位于左上角（更优区域）
  • 任务吞吐量：MotionServe 在所有机器人规模下均实现最高吞吐量，例如 X-VLA 上 2,197 tasks/hour（N=96），OpenVLA-OFT 上 900 tasks/hour（N=96），相对最佳基线提升 19.3% 和 4.3%
